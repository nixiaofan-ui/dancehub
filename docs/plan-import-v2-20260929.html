补录功能改造方案

① 截图/图片识别课表　② 补录 ↔ 预约 的语义重构
DanceHub · 2026-09-29 · 待拍板后实施

先说结论

需求 1
可行，但不能让机器直接入库。走「视觉大模型识别 → 生成可编辑的确认页 → 用户核对后批量录入」，单张成本约 1.5 分钱。你给的那张 Dance Plus 三亚图有 4 个坑，方案里逐个解决。
需求 2
你感到的「一堆 bug」确认是设计缺陷（3 处，见下），另外顺带查出 1 个真 bug（删除已预约的录入课会直接报错）。核心修法：补录时选状态 + 「预约记录」升级为「我的课表」+ 取消预约时二段确认。

一、需求 1：截图 → 课程数据

1.1 你那张图里藏着 4 个坑

先把图读一遍：Dance Plus（三亚，天涯区金鸡岭街），7 列（周一~周日）× 5 行时间段，行首是「时间 + 班别」，格子里是「舞种 + 老师」，底部还有难度图例和地址。

坑为什么难对策
只有星期，没有日期 整张图是「周一~周日」的周视图，没有具体日期。机器没法知道这是哪一周 —— 猜错就整批录到错误日期上。 流程里强制加一步「这是哪一周」，默认最近一个周一，支持一次展开 4 周
三行时间完全相同 20:00-21:30 出现三次（基础班 / 常规班），即同一时段并行开班。按时间去重会误删，按时间排序会错位。 识别时保留「班别」字段一起入库；去重键用「时间 + 课名 + 老师」而不是时间
艺术字 + 白字压黑底 舞种是蓝色夸张字体圆圈（DANCE / Jazz / Hiphop），老师名是白字叠在人像上。通用 OCR 和「表格识别」都会被判为无结构图像。 必须用视觉大模型（理解版式语义），不用传统 OCR / 表格识别接口
难度靠图例暗示 图里的难度用 ○ ◯ ◎ ◉ 符号，含义写在底部图例里，字面上看不出来。 把图例一起喂给模型，让它直接输出枚举（入门/基础/进阶/高阶）

1.2 整体流程

01 小程序
选图从相册选 1~9 张，本地压缩到 1600px
02 服务端
调视觉模型密钥只留服务端，带城市/门店名做提示

校验与规整时间合法性、星期→日期换算、去重
04 小程序
确认页逐条可改可删，人核对是唯一防线
05 服务端
批量入库一次写入，可整批撤销

原则：识别结果永远不自动入库

这正是你在录课页注释里写过的原则 ——「解析错一条不会报错、也不会有人发现，用户只会觉得这软件数据不准」。所以图片识别只负责把 90% 的体力活干掉，最后那一眼必须由人来看。宁可多一次点击，也不能让一条错课静默进库。

1.3 关键交互 1：周次选择（不可省）

识别完成后，确认页顶部固定一条：

// 识别到「周一~周日」，请确认这是哪一周
← 2026-09-21 ~ 09-27 →     [ 重复 4 周 ]

默认取「最近一个已开始的周一」；点箭头前后翻周；勾「重复 4 周」则把这张周课表展开成 4 周（月课表常见）。日期换算放在服务端做（前端时区不可靠，项目里已有这个教训）。

1.4 关键交互 2：确认页

已识别 12 节课，请核对（可改可删）

周一 09-2116:30-18:00　基础班　DANCE　老师待定✕

识别不准的典型表现是老师名字认错字（Yeye / Ss / Kris 这类短名、艺术字体、白字压人像），所以老师字段要允许留空 —— 模型不确定就该交白卷，不能编。

1.6 接口设计

POST /api/imports/parse-image        // 识别
{
  images: ["data:image/jpeg;base64,..."],   // 1~9 张
  cityId: 12, cityName: "三亚",          // 帮模型定位地址栏

→ { items: [{ weekday: 1, startTime: "16:30", endTime: "18:00",
              courseName: "DANCE", className: "基础班",
              coachName: "Yeye", difficulty: "BEGINNER" }],
    studioName: "Dance Plus", cityName: "三亚",
    address: "海南省三亚市天涯区金鸡岭街398号天成广场3楼",
    warnings: ["第 2 行老师名不清晰，已留空"] }

POST /api/imports/schedule/batch      // 确认后批量入库
{
  studioName, cityId|customCityName,
  weekStart: "2026-09-21", repeatWeeks: 4,   // 展开成 4 周
  items: [...],                              // 用户核对/修改后的最终数据
  book: "CONFIRMED"                          // 见需求 2 改动 A
}
→ { created: 48, skipped: 2, skippedDetail: [...], batchId: "..." }

两个必须提前知道的实现坑

① 图片不能用 wx.uploadFile。小程序走的是 wx.cloud.callContainer（免备案那条路），它只吃 JSON body —— 所以图片要以 base64 塞进请求体。压缩到 1600px / quality 80 后单张约 300~600KB，1~9 张完全在限额内。

② 现有请求封装的 10 秒超时会把识别打死。request.js 里 REQUEST_TIMEOUT_MS = 10000，而视觉模型出一份 12 节课的 JSON 通常要 8~25 秒。这个接口必须单独放宽到 60 秒，前端配「识别中…（大约 10 秒）」的进度态，避免用户以为卡死。

1.7 服务端后处理（这层不能省）

  1. JSON 解析失败 → 降温度重试一次；仍失败则回「识别失败，请手动录入」，不能把半截数据丢给前端。
  2. 时间校验：HH:MM 格式、结束晚于开始、时长在 30~180 分钟之间，越界丢弃并记 warning。
  3. 星期 → 日期：在服务端按 weekStart 换算，避免前端时区问题。
  4. 难度归一化：模型给的自由文本映射到库里的枚举（入门/基础/进阶/高阶/不限）。
  5. 去重：同一门店同一天「开始时间 + 课名 + 老师」已存在则标 skipped（并行班靠课名区分，不会误杀）。
  6. 门店复用：沿用现有逻辑按「同城同名」找店，找不到才建，避免同一家店出现两半课表。

1.8 风险与对策

风险程度对策
模型编造不存在的课中确认页人眼兜底；prompt 明确「不确定就留空」；给「这不是课表网格？」的失败识别专门返回错误
老师名认错字中允许留空；老师名只做展示、不参与去重键
耗时超时低单独放宽超时 + 进度态 + 失败可重试
成本失控低每人每日 20 张上限、单张 ≤5MB；月成本先按百张/天量级
图不是网格课表（纯海报/纯文字）中识别为空时不做「零结果」的死路，直接引导去手动录入

二、需求 2：补录 ↔ 预约 的语义重构

2.1 现状的三个现象，都不是偶发故障

你看到的根因性质
补录完，预约记录里没有它 「补录」只创建了课程数据（Schedule），没有创建预约记录（Booking）。两者是两张表，补录压根不碰 Booking。 设计缺陷
之前录过的课查不到 「我录的课」这份列表只做在录课页里，而录课页入口藏在「我的」的一条小字上，回看很难。真正该放的位置（预约记录 tab）里没有。 功能缺失
补录→预约→取消，课还在课表里 取消预约只删 Booking（而且是物理删除）。而补录产生的那条课程属于你（ownerId = 我），课表页本来就会把它查出来显示，跟有没有预约无关。 语义混淆

一句话总结：一个「补录」按钮同时被理解成两件事 —— 用户觉得是「记录我要上的课」，系统做的是「往库里加一条课程数据」。这两件事在数据库里分属两张表，于是走成了两条互不相识的链路。

2.2 改动 A：补录时直接选状态（你原话要的）

表单底部加一组单选，替换掉现在「录完就结束」的裸提交：

已约（我在店里已经约好了） · 默认录完同时标记为已约，会出现在「我的课表」和预约记录里。Schedule + Booking(CONFIRMED)
想上（先记下来，开课前提醒我）状态为待确认，并自动设一条开课前提醒。Schedule + Booking(PENDING) + Reminder
只记录（不约也不提醒）就是现在这个行为，只把课记进我的课表。Schedule

这样「补录」这个动作的语义就明确了：它不再是往库里投数据，而是加一节课到我的行程里。

2.3 改动 B：「预约记录」升级成「我的课表」

不新增 tab（你刚把 5 个合并成 4 个，别再拆），而是把现有「预约记录」这一栏扩成统一视图，一行看清所有我相关的课：

  • 来源标签：我录的 / 已抓取
  • 状态标签：已约 / 想上 / 只记录
  • 行内操作：没约的 → 「预约」；已约的 → 「取消预约」；我录的 → 「删除」
  • 排序：今天及以后在前，过期折叠起来

这里同时解决了「之前录过的课查不到」—— 那批数据一直都在 /api/imports/mine 里，只是没有一个正经入口。

2.4 改动 C：取消预约时二段确认

if (这节课是抓取来的公共课)
    → 只取消预约（保持现状）

if (这节课是我自己录的)
    → 「这节课是你自己录的，要一起删掉吗？」
        [ 只取消预约 ]   [ 连课一起删 ]

「连课一起删」就顺手删掉那条私有课（含它的提醒），这样课表里也不会再留着一条你早就不打算上的课 —— 正是你现在看到的现象。

2.5 改动 D：补录入口搬到「课表」页（可选，但建议做）

现在补录入口在「我的」的一条小字上，用户是「想到要去补录」才会去；而真实场景是在课表里发现某天缺课，就地想补上。

  • 课表页日期条右侧加「＋」，进入补录页时自动带上当前城市 + 当前选中日期（不用再选一次）
  • 某天空状态加一句「这家店没抓到？帮我补一节课」
  • 「我的」页入口保留，文案不变

顺带查出 1 个真 bug（现在就会报错）

删除自己录入的课，如果这节课已经被预约过，会直接失败：DELETE /api/imports/schedule/:id 只删 Schedule，而 Booking / Reminder 对它还有外键引用，数据库会拒绝这次删除，前端只看到一句莫名其妙的报错。

你现在之所以没撞上，是因为你的操作顺序恰好是先取消预约、再删课。只要有人直接删一节已约的课，就一定踩到。

修法：在事务里先删 Booking、Reminder，再删 Schedule（应用层显式删除，不改表结构 —— 云库跑 DDL 的成本和风险都比这高得多）。

2.6 服务端改动清单

接口改动
POST /api/imports/schedule加 book 参数（CONFIRMED / PENDING / null），创建课程后按需建 Booking（+ Reminder），返回 bookingId
POST /api/imports/schedule/batch 新增批量入库（图片识别用），支持 repeatWeeks 展开多周，返回 created / skipped 明细
POST /api/imports/parse-image 新增转视觉大模型 + 后处理校验，只返回结构化结果，不写库
GET /api/imports/mine返回里补 bookingStatus / hasReminder，让前端能一行显示状态与操作
DELETE /api/imports/schedule/:id修 bug 事务内级联删 Booking / Reminder（不改 schema）

2.7 小程序改动清单

  • pages/import/：加「传课表图片」入口、状态三选一、识别确认页（新增 pages/import/confirm 或页内弹层）
  • pages/profile/：「预约记录」→「我的课表」，合并显示我录的课 + 预约状态 + 行内操作
  • pages/index/：日期条加「＋」跳补录（带城市与日期）；取消预约时对我录的课弹二段确认
  • utils/request.js：给识别接口单独放宽超时
  • 跑 npm run check:register（新增页面/模块后必跑）

三、分期建议

期内容说明
P0 需求 2 全部（A+B+C+改 bug） 纯逻辑修复，不依赖任何外部服务，一次部署 + 一个体验版就能验收。你反馈的体验问题绝大多数在这一期消失。
P0 需求 1 的单张图识别 + 确认页 + 批量入库 需要先定识别平台、拿到 key。识别引擎的对接是独立的一小块，做完直接可视。
P1 多张图 / 重复 4 周 / 与已有课的去重覆盖提示 等 P0 跑通、看过真实识别率之后再做，避免提前优化。
P2 识别质量反馈闭环（记录用户改了哪些字段，用来调 prompt） 真正能把识别率从「能用」推到「好用」的一步，但要有数据之后才有意义。

四、需要你拍板

1. 识别引擎用哪个？我推荐腾讯混元视觉（与云托管同厂、约 1.5 分/张）；也可以选阿里 Qwen3-VL（约 3 分/张，中文版式更强）。定了之后需要你给一个 API Key，我只放进云托管环境变量。
2. 补录后的默认状态选哪个？我建议默认「已约」—— 会去补录一节课的人，十有八九是这节课真要去上。另两个选项仍然保留。
3. 补录入口要不要搬到课表页？搬（课表页「＋」，自动带城市和日期，同时保留「我的」入口）还是先只修逻辑不动入口。
4. 先做哪一半？我建议需求 2 先做（不依赖外部服务、当天可验证），需求 1 并行等你给 key。也可以两件一起上。
